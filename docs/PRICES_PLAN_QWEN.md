# План: цены лабораторий + оптимизация по стоимости (соответствие макету v5.html)

Документ: сопоставление макета `v5.html` (ветка main, Occupancy3537/Vita) с текущим
кодом и план реализации цен на анализы внутри существующей оптимизации сдачи.
Дата: 2026-09-29. Ветка: qwen-uiux-roadmap.

## 1. Что обещает макет v5 (зафиксировано в его ПЛАНЕ СБОРКИ, п.12 и коде)

- Карточка «Следующая сдача»: дата · число анализов · **цена в выбранной лаборатории** · поводы.
- Шторка «Что сдаём» = аккордеоны: Состав · **«Лаборатория и цена»** · Оптимизатор.
- Секция «Лаборатория и цена»: итог (`X ₽ · lab · N пробирок · ~M мл`), **чипы лабораторий
  с ценой**, выбор чипом, отметка «дешевле всего».
- Вопрос оптимизатора прямо в карточке со **скидкой в рублях** («Ферритин → декабрь — −380 ₽»),
  история решений в секции «Оптимизатор».
- Прямо в коде макета: `НОВОЕ: price_rub по лабораториям, объём крови по пробиркам`.
- Данные макета фейковые: `labs:[['Хеликс',2980],['Гемотест',3120],['Инвитро',3450]]` —
  одна цифра на панель, без состава и без комплексов.

## 3. Целевая модель данных (принять до кода)

Новый слой `card.lab_price` (или кэш в памяти из Google Drive JSON):

```
lab_key        "helix" | "invitro" | "gemotest"      (справочник labs: id, название, адрес/зона)
item_type      "single" | "complex"                   (анализ ИЛИ чекап/комплекс)
code           M0xx                                   (для single — код нашего каталога)
complex_id     uuid                                   (для complex)
members        [M0xx...]                              (для complex: состав, canonical-коды!)
price_rub      int
valid_from / parsed_at                                (дата прайса — обязательный дисклеймер)
```

Ключевые решения:
1. **Маппинг названий** — отдельная таблица `lab_alias` (canonical code ↔ строка прайса лабы).
   Парсер по fuzzy-match пишет незнакомые позиции в очередь на ручное подтверждение;
   никогда не матчит молча (риск: «Железо сывороточное» ≠ «Железо ОЖСС»).
2. **Состав комплекса — только canonical-коды.** Парсер/куратор раскрывает чекап в список
   маркеров один раз руками+полуавтоматически; дальше оптимизатор работает с множествами.
3. Все расчёты — на бэкенде (архитектурное решение из обсуждения трёх мнений); клиент
   получает готовый `offer` для выбранной панели.

## 4. Алгоритм оптимизации внутри лаборатории (ядро задачи)

Вход: множество кодов ближайшей панели P (уже считает `lab_optimizer`), лаба L, прайс L.
Для каждой лабы решаем **set cover с минимальной стоимостью**:

```
варианты покрытия P в L:
  A) все точечно:                sum(price_single[c] for c in P if c в прайсе)
  B) один комплекс K ⊆...:       price(K) + точка(остаток)   — для каждого K из прайса L
  C) несколько комплексов + точка — комбинации ограничить: парные проверки для |P|≤12
ограничения:
  - комплекс считаем выгодным, только если покрывает ≥2 маркера из P
    (иначе это просто дорогой одинарный тест);
  - маркер отсутствует в прайсе L → вариант с дыркой помечается «N анализов L не делает»,
    сравнение честных вариантов только между полностью покрывающими;
  - fallback: жадный выбор (сортировка комплексов по цене за новый покрытый маркер),
    при |P| > 14 — только greedy; полный перебор комплексов — офлайн-прекомпиляция
    на каждую неделю загрузки прайсов, результат в кэш.
```

Мета-оптимизация (не ломает текущую логику дат!):
- **Выбор лабы может двигать дату**: если в дешевой лабе ближайший слот позже — показывать
  компромисс «Хеликс дешевле на 640 ₽, но на 3 дня позже» как отдельный offer, не молча.
- Пробирки/натощак остаются сквозными ограничениями: панель формируется сначала по дате и
  пробиркам (текущий движок), затем внутри готового состава считается лучший offer по лабам.
- Перенос ради скидок (как ферритин −380 ₽ в макете) — надстройка над already существующим
  механизмом shifted: candidate-move оценивается в рублях по delta-цене обеих панелей.

Выход для API (новая форма `next_draw`, обратно совместимая):

```json
"labs": [{"key":"helix","name":"Хеликс","price_rub":2980,"covered":10,"missing":["M079"]}, ...],
"pick": {"lab":"helix","price_rub":2980,"tubes":[3,12],"ml":47,
         "breakdown":[{"kind":"complex","name":"Железо экспресс","covers":["M021","M022"],"price":890},
                      {"kind":"single","code":"M004","price":350}],
         "cheapest": true, "price_valid_until":"2026-10-05"},
"alt_labs_note": "Гемотест +140 ₽ · Инвитро не делает Lp(a)"
```

## 5. Соответствие UI макету v5 (строго по утверждённому макету)

Ничего нового не изобретаем, достраиваем ровно нарисованное:

1. **Карточка «Следующая сдача»** (`#nextDraw`, vita.html renderDoctor): добавить `· {pick.name}`
   рядом с ценой — макет: `12 анализов · 3 360 ₽ · Хеликс · натощак`.
2. **Шторка «Что сдаём»**: завести третий аккордеон «Лаборатория и цена» (CSS `.labSum/.lchip`
   уже в файле): строка итога pick + чипы лаб, тап по чипу = пересекция (fetch с `?lab=`),
   у самого дешёвого чипа подпись «дешевле всего» (ровно как в макете).
3. **Блок breakdown** («почему такая цена») — раскрывается внутри аккордеона: комплексы
   показать строкой «Чек-ап „Железо" — 2 анализа, 890 ₽ (выгоднее на 210 ₽)» — это и есть
   учёт скидок для пользователя, одной строкой, без таблицы из 12 цен (продакт-решение из
   трёх мнений: 2–3 варианта, не маркетплейс).
4. **Секция «Оптимизатор»** = ferHist()-подобный список решений, теперь с рублями:
   «B12+MMA в одну пробирку», «ферритин → декабрь −380 ₽», «Lp(a) точечно: Хеликс не делает».
5. **Empty/stale states** (UI-решение): нет прайсов → текст уже заложен в vita.html:1759
   («Цены по лабораториям пока не заведены»); прайс старше 7 дней → бейдж «прайс от ДД.ММ,
   уточните»; маркер без цены → «N позиций без цены, итог — нижняя граница».
6. Табы дат (`dpill`) — в макете кликабельны, в коде статичны: при добавлении цен сделать
   переключение панели живым (GET /labs/plan уже отдаёт все панели).

## 6. Этапы реализации

**Этап 0 — данные (0.5–1 нед).**
- Схема `lab_price` + справочник `lab`, миграция в migrations/.
- Загрузчик JSON с Google Drive (weekly scheduler проекта уже есть) → нормализация → upsert;
  версия прайса `parsed_at` в каждой строке.
- `lab_alias`: первичный маппинг ~80 маркеров × 3 лабы полуавтоматически (fuzzy + ручная
  приёмка одним экраном/скриптом). Без маппинга дальше идти нельзя.

**Этап 1 — цены точечно (≈3–4 дня).**
- `price_of(L, code)`; в `_render_panel` вместо одного `total_price_rub` — `labs[]` с суммой
  точечно + `missing[]`; детерминизм сохранить (sorted, без dict-обходов).
- `/labs/plan?lab=helix` → pick; `shape_doctor.next_draw.labs/pick`.
- Фронт: чипы в шторке + подпись лабы в карточке. Пользователь уже видит «самая дешевая лаба»
  по одиночным анализам. Тесты: test_lab_optimizer расширяется фикстурами прайса.

**Этап 2 — комплексы (≈1 нед).**
- Кураторский справочник complexes (состав в canonical-кодах, старт: 8–15 популярных чекапов
  3 лаб, покрывающих наши категории PhenoAge/сердце/железо/гормоны).
- Set-cover-offer (раздел 4) + кэш результатов по (hash(P), version_pricelist).
- Breakdown в UI (этап 5.3), выгода комплекса в рублях.

**Этап 3 — мета-оптимизация (по желанию, ≈3 дня).**
- Рублёвые предложения переносов (расширить механизм shifted: «перенести X → −Y ₽»),
  история решений с рублями в секции «Оптимизатор».
- Компромисс цена↔дата («дешевле, но позже») как alt-offer.

**Приоритетные правила (конфликт критериев):** безопасность/сроки врача > пробирки и даты
(текущий движок) > цена. Цена никогда не двигает срок раньше due_date и не разбивает панель
ради экономии, если это добавляет забор.

## 7. Риски

- Качество маппинга названий — главный риск; mitigation: очередь неподтверждённых строк,
  fuzzy ниже порога = «нет цены», а не «примерно то».
- Прайсы лаб меняются чаще недели (акции) — держать дисклеймер «последняя проверка ДД.ММ».
- Комплекс может включать маркеры, которые Влад уже сдавал недавно, — покрытие считаем только
  по P панели; лишний состав комплекса показывать честно («в комплекс входят ещё 4 — про запас»).
- Монолит vita.html: новые секции писать в существующие функции renderPanel/draw(), не плодя
  параллельных компонентов (см. docs/UIUX_ROADMAP_QWEN.md, пункт 6).
