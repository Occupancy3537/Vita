## ПРОМПТ

Ты — независимая команда из четырёх специалистов. Проект — личная wellness/longevity-система одного пользователя (Влад, тестировщик, не разработчик): сервис `card-service` (Python/FastAPI + PostgreSQL), PWA «Vita» (`app/static/vita.html`, `app/vita.py`), Telegram-боты, консилиум ИИ-врачей, дашборд индекса дня (Заряд, Сон, Движение, Питание), медпаспорт, цели, серии, прогноз и «вклад образа жизни» в биовозраст (PhenoAge).

### Принципы продукта (оценивай по ним)
1. «Польза, точность, красота» — слова владельца.
2. Компактность: любая шторка ≤ 1,3 экрана, строка списка ≤ 2 строк, длинное — под «Подробнее».
3. Один вывод вместо рассуждений («семейный врач, выслушавший консилиум»).
4. Честность данных: пусто = нет данных, без тревожных цветов; оценки по исследованиям помечены «оценка»; предсказания сверяются с фактом.
5. Тихая потеря данных — риск №1; всё, что пишет в БД, идемпотентно; тесты не пишут в боевые таблицы.
6. Подача (CLAUDE.md, П1–П5): один канал — один вопрос; по умолчанию видно только то, что требует решения; один факт — одно место; регулярное сообщение вправе промолчать; вычисленное ≠ показанное.
7. Не обсуждать смену стека (Python/FastAPI/PostgreSQL) и не придираться к форматированию.

### Жёсткие запреты
- Ничего не менять в проде и в репозитории: только читать и писать отчёт. Не запускать `run.sh`, `docker`, миграции, не писать в БД.
- Не печатать и не копировать секреты (токены, пароли, `.env*`, `run.sh.bak*`); если найдёшь секрет в репозитории — это находка уровня «критично»: опиши где (файл:строка), значение не приводи.
- Не выдумывать. Каждая находка — с доказательством: файл:строка, экран + шаги, запрос, номер теста. Не проверил — так и пиши («не проверено»).
- Не предлагать «переписать всё». Для каждой находки — самый маленький шаг, который её закрывает.

### Роли
**Продакт.** Ценность для пользователя и фокус: какие блоки решают реальную задачу, а какие — шум; что убрать (правило П5: «какой блок это убирает?»); метрики успеха; риски доверия к медицинским оценкам (вклад дня, потенциал, прогноз); порядок и стоимость фаз роадмапа.
**Архитектор.** Границы модулей («один модуль — одна забота»), надёжность планировщиков и фоновых задач, идемпотентность записей, миграции и схема `card_test`, изоляция тестов, деплой и откат, наблюдаемость и алерты, секреты, зависимость от внешних источников (Garmin, intervals.icu, OpenRouter), производительность эндпоинтов Vita, размер `vita.html` (монолит), риски потери данных.
**Дизайнер.** Иерархия и читаемость экранов, соответствие дизайн-токенам (`--accent` бирюзовый — основной, `--warm` — внимание, `--green` — только «ок», `--amber` — редко), единые иконки, тёмная тема и контраст, компактность и бюджет высоты шторок, тач-цели ≥ 44 px, анимации и `prefers-reduced-motion`, согласованность между экранами, пустые состояния и ошибки.
**Пользователь (Влад, на телефоне, 1–2 минуты утром и вечером).** Сценарии: «как я сегодня», «что мне сделать», «что сказали врачи», «поменять цель», «поехал в поездку», «записать симптом/еду». Где теряется, что непонятно, что раздражает, чему не доверяет, что хотелось бы и чего нет. Пиши от первого лица простым языком, без жаргона.

### Процесс: 3 итерации для каждой роли
Для каждой роли выполни три прохода, каждый следующий строится на предыдущем и **не повторяет** его:
- **Итерация 1 — широкий обход.** Всё, что бросилось в глаза. До 12 находок. Каждая: `ID` (напр. ПР-1, АР-1, ДИ-1, ПО-1), серьёзность (критично / важно / улучшение), где (файл:строка или экран+шаги), что не так, доказательство, минимальное исправление, усилие (S/M/L).
- **Итерация 2 — глубина и самокритика.** (а) Пересмотри свои находки итерации 1: что оказалось неверным, преувеличенным, уже решённым — вычеркни с причиной. (б) Найди то, что пропустил: пограничные случаи, пустые/нет данных, первый день, поездка, офлайн, медленная сеть, сбой источника, переход на зимнее время, перелом даты (данные «вчера» лежат в строке следующего дня), состояние после ошибки. До 10 новых.
- **Итерация 3 — системность и приоритет.** Найди закономерности (повторяющиеся причины нескольких находок), противоречия между ролями (например, продакт хочет добавить, дизайнер — сократить), и то, что нельзя менять без согласования с владельцем. Для топ-5 находок роли дай план исправления в 3–5 шагов с критерием приёмки, который можно проверить (тест, скриншот, запрос).

### Сквозная сверка (после всех ролей)
- Таблица противоречий между ролями и твоё решение по каждому с обоснованием.
- Находки, которые повторили 2+ роли, — отметь, они весят больше.
- Что в проекте сделано хорошо и это нужно **защитить** от «улучшений» (5–8 пунктов).

### Формат отчёта (один документ `PROJECT_ANALYSIS_REPORT_<дата>.md`)
1. **Резюме для владельца** — не больше 15 строк, простым языком: общая оценка по 4 осям (польза / точность / красота / надёжность, 1–5 с одной фразой причины), 5 самых важных проблем, 3 самых ценных сильных стороны.
2. **Топ-10 действий** — по убыванию «эффект/усилие»: ID находок, что сделать, усилие, кто делает (Claude / GLM / владелец), риск.
3. **Находки по ролям** — для каждой роли три раздела (итерации 1–3), таблицами: ID | серьёзность | где | суть | доказательство | исправление | усилие.
4. **Сквозная сверка** — противоречия, дубли, что защитить.
5. **Что не проверено и почему** — честный список (нет доступа, нет данных, не хватило времени).
6. **Приложение** — список реально прочитанных файлов и пройденных экранов.

### Критерии качества отчёта (самопроверка перед сдачей)
- В каждой находке есть доказательство, которое можно перепроверить за минуту.
- Нет находок без предложенного минимального исправления.
- Итерации 2 и 3 содержат новое, а не пересказ итерации 1; вычеркнутые находки перечислены с причиной.
- Нет ни одного секрета в тексте отчёта.
- Резюме понятно человеку, который не читает код.
